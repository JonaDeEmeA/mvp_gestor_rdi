Principios:
- Los componentes React nunca acceden a IndexedDB directamente
- Los hooks orquestan lógica de negocio y llaman a repositorios
- Los repositorios implementan una interfaz intercambiable
- La capa de storage maneja solo operaciones crudas de base de datos
2. Modelo de Dominio

interface ProgressGroup {
  id: string;
  name: string;
  description: string;
  progress: number;           // 0-100

interface GroupElement {
  id: string;

// /src/domain/models/ProgressSnapshot.ts
interface ProgressSnapshot {
  id: string;
  groupId: string;           // FK -> ProgressGroup.id
  progress: number;          // 0-100
  comment: string;
  createdAt: string;         // ISO date
  createdBy?: string;
}

// /src/domain/models/SnapshotPhoto.ts
interface SnapshotPhoto {
  id: string;
  snapshotId: string;        // FK -> ProgressSnapshot.id

  caption: string;
  createdAt: string;         // ISO date
}

4. Estrategia de Repositorios
Interfaz abstracta (contrato):
// src/repositories/interfaces/IProgressRepository.ts

interface IProgressRepository {
  // Grupos
  getGroups(): Promise<ProgressGroup[]>;
  getGroupById(id: string): Promise<ProgressGroup | null>;
  createGroup(data: Omit<ProgressGroup, 'id' | 'createdAt' | 'updatedAt'>): Promise<ProgressGroup>;
  updateGroup(id: string, data: Partial<ProgressGroup>): Promise<ProgressGroup>;
  deleteGroup(id: string): Promise<void>;

  // Elementos
  getElementsByGroup(groupId: string): Promise<GroupElement[]>;
  addElement(groupId: string, ifcGuid: string): Promise<void>;
  removeElement(groupId: string, ifcGuid: string): Promise<void>;
  getGroupsByElement(ifcGuid: string): Promise<ProgressGroup[]>;

  // Snapshots
  getSnapshotsByGroup(groupId: string): Promise<ProgressSnapshot[]>;
  createSnapshot(data: Omit<ProgressSnapshot, 'id'>): Promise<ProgressSnapshot>;

  // Fotos
  getPhotosBySnapshot(snapshotId: string): Promise<SnapshotPhoto[]>;
  addPhoto(data: Omit<SnapshotPhoto, 'id'>): Promise<SnapshotPhoto>;
}
Implementación IndexedDB:
Archivo único: src/repositories/IndexedDBProgressRepository.js
- Implementa todos los métodos de la interfaz usando promesas
- Maneja apertura de DB con esquema de versionado
- Usa transacciones correctas (readwrite vs readonly)
- Los métodos devuelven objetos planos (no modelos de dominio)
Migración futura a Firebase:
Se crearía FirebaseProgressRepository.js implementando la misma interfaz. El cambio en los hooks sería:
// Antes:
const repo = new IndexedDBProgressRepository();

// Después:
const repo = new FirebaseProgressRepository(firebaseApp);
Sin cambios en componentes ni lógica de negocio.
5. Estrategia de Almacenamiento de Fotografías
Análisis comparativo:
Estrategia	Almacenamiento	Rendimiento	Migración Futura	Recomendado MVP
Base64	~33% más grande que binario	Codificación/decodificación costosa en cada carga	Fácil (string portable)	❌
Blob	Binario nativo, sin overhead	Óptimo, IndexedDB lo soporta nativamente	Requiere manejo de Blob → Firebase Storage	✅
Object URLs	Solo referencia en memoria, no persistente	Muy rápido para visualización	No persistente	❌ para almacenamiento
Decisión: Blob + Object URL para visualización
Justificación:
1. IndexedDB almacena Blobs nativamente sin conversión
2. Para mostrar la imagen: URL.createObjectURL(blob) → se renderiza en <img>
3. Sin overhead de codificación Base64 (ganancia del 33% en espacio)
4. La migración a Firebase Storage es directa: blob → uploadBytes()
Flujo de captura y almacenamiento:
Cámara/dispositivo → File/Blob → IndexedDB (SnapshotPhotos.imageData)
                                   ↓
                            URL.createObjectURL() → <img> preview
                                   ↓
                            Revocar URL al desmontar componente
Límite MVP: Máximo 5 fotos por snapshot. Las imágenes se redimensionan a 1200px en el lado más largo antes de almacenar.
6. Estrategia de Visualización BIM
Sistema de Color por Avance
Rango de Avance	Color	Código
0%	Gris neutro	#888888
1% – 49%	Amarillo	#FFC107
50% – 99%	Azul	#2196F3
100%	Verde	#4CAF50
Implementación Técnica
Se usará el sistema de materiales por fragmento de ThatOpen, no el Highlighter:
// Pseudocódigo del approach
const fragmentsManager = components.get(OBC.FragmentsManager);
const fragmentMap = fragmentsManager.list;

// Para cada grupo de avance:
for (const element of groupElements) {
  const fragmentId = guidToFragmentMap.get(element.ifcGuid);
  if (!fragmentId) continue;

  const fragment = fragmentMap.get(fragmentId.modelId);
  const color = getProgressColor(group.progress); // THREE.Color
  
  // No crear material único por elemento.
  // Usar colorSets del fragmento para modificar colores de instancia.
  fragment.setColor([color.r, color.g, color.b], fragmentId.instanceId);
}
Optimizaciones de rendimiento:
- No se crean materiales por elemento, se usa setColor() a nivel de instancia de fragmento
- Se mantiene un mapa guid → { modelId, instanceId } calculado al cargar el modelo
- Los colores se agrupan por fragmento para minimizar llamadas
- Los cambios de color se aplican en lote con fragmentsManager.core.update(true)
Estado inicial (modelo recién cargado):
Todos los elementos en gris (0%) por defecto, hasta que se asocien a grupos.
7. Estrategia de Compatibilidad con Nuevas Versiones IFC
Estrategia basada en GlobalId
Problema: Cuando se recarga un IFC modificado, los ExpressID cambian. Los GlobalId persisten.
Solución:
1. Al cargar el modelo IFC, se construye un mapa bidireccional:
GlobalId → { modelId, instanceId (expressID) }
2. Este mapa se recalcula en cada carga del modelo
3. Los grupos de avance solo almacenan GlobalIds
4. La visualización consulta el mapa para resolver colores
Detección de cambios:
- GlobalIds nuevos → elementos agregados (aparecen en gris)
- GlobalIds faltantes vs registros existentes → elementos eliminados (se marcan como "no encontrados" pero se conservan en BD)
- GlobalIds existentes → colores normales según avance
Mitigaciones:
Riesgo	Mitigación
Elemento eliminado del IFC pero con historial	Se muestra advertencia visual, historial preservado
ExpressID diferente tras recarga	No afecta porque todo se resuelve por GlobalId
Grupo con GUIDs que ya no existen	Se marca grupo como "parcial", se notifica al usuario
8. Riesgos Técnicos Identificados
#	Riesgo	Impacto	Probabilidad	Mitigación
R1	Degradación de rendimiento con >50,000 elementos coloreados	Alto	Media	Usar setColor() por instancia de fragmento, no highlightByID
R2	Fotografías grandes saturan IndexedDB	Medio	Alta	Redimensionar a 1200px, límite de 5 fotos/snapshot
R3	Blobs en IndexedDB pueden causar cuotas excedidas	Medio	Baja	Monitorear navigator.storage.estimate(), mostrar advertencia
R4	El GlobalId no se extrae actualmente del IFC	Alto	Alta	Implementar en Fase 1, modificar usePropertySelection
R5	La interfaz de repositorio en JS no tiene enforcements de tipos	Medio	Alta	Usar JSDoc + convención, migrar a TS en fase posterior
R6	Object URLs no liberadas causan memory leaks	Bajo	Alta	Limpieza en useEffect return, hook dedicado useObjectURL
9. Riesgos Funcionales Identificados
#	Riesgo	Impacto	Mitigación
F1	Usuario en terreno sin conexión	Alto	IndexedDB funciona offline, diseño offline-first
F2	Confusión entre ExpressID y GlobalId	Alto	Documentación clara, validación en repositorio
F3	Usuario asigna 100% pero obra no terminada	Medio	Historial permite revertir, sistema de aprobación opcional
F4	Fotografías sin modelo de referencia	Medio	Al tomar foto, guardar viewpoint asociado
F5	Múltiples usuarios editando sin sincronización	Bajo (MVP)	Postergado para Firebase migration

13. Estrategia Futura de Migración a Firebase
Plan de migración:
1. Crear FirebaseProgressRepository implementando IProgressRepository
2. Cada objeto store de IndexedDB → colección Firestore:
- ProgressGroups → progressGroups/{id}
- GroupElements → groupElements/{id} (con índice compuesto groupId+ifcGuid)
- ProgressSnapshots → progressSnapshots/{id} (con índice groupId)
- SnapshotPhotos → Firebase Storage (no Firestore) en photos/{snapshotId}/{photoId}.jpg
3. Estrategia de sincronización: offline-first con Firestore persistence habilitada
4. Las fotos migran de Blob en IndexedDB → Firebase Storage
5. Autenticación: ya existe Firebase Auth en el proyecto
Lo que NO cambia:
- Los modelos de dominio
- Los componentes React
- Los hooks de lógica de negocio
- La visualización BIM
Lo que SÍ cambia:
- El repositorio inyectado
- useProgressManager recibe repositorio diferente
- Se agrega sincronización en tiempo real (opcional)
Estrategia Híbrida Recomendada (Grupos)
Para el MVP, recomiendo grupos exclusivamente manuales.
Justificación:
1. Los grupos automáticos requieren parseo completo de propiedades IFC (IfcRelAggregates, IfcRelContainedInSpatialStructure), lo que añade complejidad significativa
2. El valor de negocio del MVP es validar el flujo: crear grupo → asignar elementos → reportar avance → ver colores
3. Los grupos automáticos se pueden agregar en Fase 8 sin cambios en el modelo de datos
4. La selección manual permite al usuario agrupar elementos de diferentes categorías/niveles en un mismo grupo (ej: "Fachada Norte" que incluye muros, ventanas y puertas)
Estrategia futura: En Fase 8, se agregaría un botón "Generar desde niveles" que consultaría el IFC y propondría grupos basados en IfcBuildingStorey. El usuario podría aceptarlos o modificarlos antes de confirmar.
